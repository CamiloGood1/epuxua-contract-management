Resumen Ejecutivo

El sistema presenta una base de ingeniería sólida y un nivel de madurez funcional avanzado. Sin embargo, se identificaron 4 vulnerabilidades críticas — dos de ellas de seguridad directa — que deben corregirse antes de cualquier expansión a múltiples entidades o exposición a auditorías externas (Contraloría, Procuraduría, Control Interno, Revisoría Fiscal).

Veredicto de madurez: El sistema está listo para uso interno controlado con roles asignados. No está listo para producción multi-entidad hasta resolver los hallazgos críticos C01–C04. Una vez corregidos, la arquitectura base soporta el crecimiento proyectado.

Fortalezas y Debilidades

✓ Fortalezas

  • Arquitectura Next.js App Router bien aplicada — Server Actions, Server Components, rutas API diferenciadas
  • Sistema de roles bien modelado (8 roles, funciones de acceso centralizadas en access.ts)
  • Audit log en todas las operaciones de escritura críticas (interadmin_audit_log)
  • Centro de Integridad de Datos: 13 reglas financieras de validación pura, con SQL fix sugerido por hallazgo
  • Módulo de IA modular (document-reader → content-cleaner → openai-analyzer → result-normalizer)
  • Tipos TypeScript por dominio bien separados (/types): contrato, modificaciones, rendimientos, facturas…
  • Validación de acceso por proyecto (interadmin_assignments) en escritura general
  • Rollback manual en createFinancialReturn (aunque mejorable con transacciones reales)

✗ Debilidades

  • Middleware de autenticación nombrado incorrectamente — no ejecuta en Next.js
  • Endpoint de IA expuesto sin autenticación
  • assertFinancialWriteAccess no verifica acceso por proyecto
  • Tipos Supabase no generados — as never en 50+ lugares bypasea TypeScript
  • Overfetch masivo: select("*") + limit(20000) sin paginación
  • Sin transacciones DB — datos financieros pueden quedar en estado inconsistente
  • Modelo financiero dual (campos legacy en DB + cálculo dinámico)
  • Cliente Supabase legacy (src/lib/supabase.ts) sin sesión — puede bypassear RLS

🔴 Hallazgos Críticos

Pueden generar pérdida de datos, acceso no autorizado o incumplimiento normativo. Deben corregirse antes de cualquier despliegue ampliado.

C01 — Middleware de autenticación inactivo
Crítico · Seguridad
src/proxy.ts Arquitectura

Next.js App Router requiere que el middleware se llame exactamente middleware.ts y esté en src/ o en la raíz del proyecto. El archivo actual se llama proxy.ts y exporta una función proxy() — Next.js lo ignora completamente como middleware. Esto significa que ninguna ruta está protegida a nivel Edge/middleware.

El sistema funciona porque cada Server Component llama individualmente a getCurrentUserProfile(). Pero esto es frágil: cualquier ruta API o Server Component que no llame explícitamente a esa función queda expuesta.

Solución: Renombrar src/proxy.ts → src/middleware.ts y renombrar la función exportada de proxy a middleware.
export async function middleware(request: NextRequest) { ... }
C02 — Endpoint de IA sin autenticación
Crítico · Seguridad
src/app/api/document-analysis/extracto-bancario/route.ts

El endpoint POST /api/document-analysis/extracto-bancario no verifica sesión antes de procesar el archivo y llamar a la API de OpenAI. Cualquier agente externo puede enviar peticiones ilimitadas, generando costos no controlados en la cuenta de OpenAI y exponiendo la capacidad de análisis documental sin control.

Por contraste, el endpoint /api/document-analysis/unified sí verifica sesión correctamente. Este endpoint fue agregado posteriormente y el patrón no se copió.

Solución: Agregar al inicio del handler:
const profile = await getCurrentUserProfile().catch(() => null)
if (!profile) return NextResponse.json({ error: "No autorizado" }, { status: 401 })
C03 — Aislamiento por proyecto ignorado en rendimientos financieros
Crítico · Integridad
src/services/interadmin-access.ts:84 Rendimientos Financieros

La función assertFinancialWriteAccess(_interadminId) tiene el parámetro interadminId prefijado con guion bajo (_), indicando que nunca se usa. La función solo valida el rol del usuario (ADMIN, GERENTE, SUBADMINISTRATIVA), pero no si el usuario tiene acceso al contrato específico.

Resultado: un usuario con rol SUBADMINISTRATIVA puede crear, editar o eliminar rendimientos de cualquier contrato interadministrativo, incluyendo los de otras secretarías o áreas, sin estar asignado a ellos.

Solución: Agregar verificación de asignación dentro de assertFinancialWriteAccess, similar a assertInteradminWriteAccess, para roles que no son ADMIN o GERENTE. Definir si SUBADMINISTRATIVA debe tener acceso global o solo a sus asignaciones.
C04 — Sin transacción DB: datos financieros pueden quedar incompletos
Crítico · Integridad de Datos
src/services/financial-returns.actions.ts:127 Base de Datos

El flujo de creación de un rendimiento financiero realiza dos inserciones separadas: primero en interadmin_financial_returns, luego en interadmin_financial_return_distribution. Si la segunda falla, se intenta un DELETE manual sobre el primero — pero ese DELETE también puede fallar silenciosamente.

Esto puede dejar registros de rendimiento sin su distribución de fuentes, rompiendo el modelo financiero y generando discrepancias que serían detectadas por una auditoría de la Contraloría.

El mismo riesgo existe en actualizaciones que requieren borrar y recriar distribuciones (updateFinancialReturn línea 255).

Solución inmediata: Agregar manejo de error en el rollback y retornar error explícito si el DELETE falla.
Solución definitiva: Usar una función PostgreSQL (RPC) en Supabase que encapsule ambas inserciones en una transacción atómica.

🟠 Hallazgos Altos

Deben corregirse antes de escalar a producción o a múltiples entidades.

A01 — Tipos Supabase no generados: as never en 50+ queries
Alto · Calidad
Todos los servicios

Todas las queries a tablas propias (como interadmin_financial_returns, interadmin_adiciones, etc.) usan el cast as never para suprimir errores de TypeScript. Esto significa que cualquier cambio en el schema de la base de datos — agregar, renombrar o eliminar una columna — no produce error de compilación. Los errores aparecen solo en tiempo de ejecución.

Supabase CLI genera tipos completos de todas las tablas automáticamente con un solo comando. Es la solución oficial y elimina la necesidad de as never.

Solución: npx supabase gen types typescript --project-id [PROJECT_ID] > src/types/supabase.generated.ts
Luego crear un cliente tipado y reemplazar gradualmente los as never con tipos reales.
A02 — Overfetch masivo sin paginación
Alto · Rendimiento
src/services/projects.service.ts src/app/(app)/administracion/integridad/page.tsx

El sistema carga datos con select("*") sin especificar columnas (transfiere todo el row) y con límites como .limit(5000) y .limit(20000) sin paginación real. La página de Integridad carga hasta 20.000 adiciones y 5.000 contratos en una sola petición.

A medida que crezca el número de contratos y modificaciones, estas queries agotarán el timeout de Supabase (30s por defecto) y degradarán drásticamente el tiempo de carga.

Solución a corto plazo: Especificar solo las columnas necesarias en cada query.
Solución a largo plazo: Implementar paginación cursor-based y carga progresiva en tablas grandes.
A03 — Sin rate limiting en endpoints de IA
Alto · Seguridad / Costos
src/app/api/document-analysis/

Los endpoints de análisis documental no tienen control de tasa de llamadas. Un usuario con sesión válida puede enviar cientos de PDFs por minuto, generando costos elevados en OpenAI y potencialmente agotando las cuotas de la cuenta.

Para una entidad pública que debe rendir cuentas de sus gastos tecnológicos, los costos de IA sin control son un riesgo de Control Interno.

Solución: Implementar rate limiting por usuario (ej. máximo 20 análisis/hora) usando Upstash Redis o una tabla de cuotas en Supabase. Registrar cada uso de IA en el audit log con el costo estimado en tokens.
A04 — Cliente Supabase legacy sin sesión activo en código
Alto · Seguridad
src/lib/supabase.ts

El archivo src/lib/supabase.ts crea un cliente Supabase estático (createClient) con la anon key, sin cookies de sesión. Este cliente ignora la sesión del usuario autenticado. Si cualquier Server Component lo importa en lugar del cliente correcto (createSupabaseServerClient()), las queries pueden ejecutarse con anonimato, bypasseando completamente las RLS Policies.

Adicionalmente, el archivo lanza un error a nivel de módulo si las env vars no están — esto puede romper el proceso de build en CI/CD.

Solución: Verificar que ningún Server Component importa desde src/lib/supabase.ts. Si el archivo no se usa, eliminarlo. Si se usa en el cliente (browser), mantenerlo solo para operaciones que no requieran sesión de usuario.
A05 — syncFundingGroups como side effect en render de página
Alto · Fiabilidad
src/app/(app)/proyectos/[id]/page.tsx:80

La función syncFundingGroups() (que crea o actualiza grupos de financiación) se llama en el cuerpo de un Server Component de página, durante el render. Su error es silenciado con .catch(() => {}).

Esto implica: (1) cada visita a la página de detalle ejecuta una escritura en base de datos, (2) si falla, el usuario no recibe ningún aviso y las fuentes de financiación pueden quedar desincronizadas, (3) el render no debería tener side effects de escritura según el modelo de React Server Components.

Solución: Mover syncFundingGroups a un Server Action explícito que se llame solo cuando haya un cambio real en adiciones (no en cada render). Usar un campo needs_sync o un timestamp de comparación.

🟡 Hallazgos Medios

Conviene corregir antes de escalar. No son urgentes, pero generan deuda técnica que se acumula.

M01 — Modelo financiero dual: campos legacy + cálculo dinámico
Medio · Integridad

La tabla interadministrativos tiene campos denormalizados (adicion, total_cuota_admin, bolsa_gerencia_inicial, adicion_bolsa_mandato, total_bolsa_mandato) que duplican valores que también se calculan dinámicamente desde interadmin_adiciones. El módulo de Integridad ya detecta inconsistencias (reglas R01–R07), lo que confirma que la divergencia ocurre en producción.

Para una auditoría fiscal, la existencia de dos fuentes de verdad para el mismo valor (ej: total de adiciones) es un hallazgo de riesgo alto.

Solución a largo plazo: Definir formalmente cuál es la fuente de verdad para cada valor. Deprecar los campos legacy en la DB y alimentarlos solo mediante vistas computadas o triggers. Documentar la decisión.
M02 — Sin paginación en ninguna tabla de la UI
Medio · Rendimiento / UX

Todas las tablas de datos (modificaciones, rendimientos, facturas, contratos derivados) cargan todos los registros de una vez y los renderizan en el DOM. Actualmente esto funciona por el volumen moderado de datos, pero con el crecimiento proyectado (miles de modificaciones, cientos de contratos por entidad), degradará la experiencia notablemente.

M03 — Validación de archivo solo por extensión
Medio · Seguridad
src/lib/document-analyzer/document-reader.ts

El document-reader verifica el tipo de archivo únicamente por el nombre (file.name.endsWith('.pdf')). Un archivo con extensión .pdf pero contenido arbitrario pasará la validación y se enviará al parser. Si pdf-parse tiene vulnerabilidades en su manejo de payloads malformados, este es el vector de entrada.

Solución: Verificar el MIME type real del archivo (file.type === 'application/pdf') y los primeros bytes mágicos del buffer (%PDF) antes de procesarlo.
M04 — maxDuration = 45s puede exceder límites de hosting
Medio · Infraestructura
src/app/api/document-analysis/unified/route.ts:9

La ruta de análisis unificado declara export const maxDuration = 45. En Vercel Free Tier, el límite es 10 segundos; en Pro, 60 segundos. Si la plataforma está en Free Tier, las funciones de análisis de documentos complejos serán terminadas antes de completar. El análisis de un PDF de 40 páginas puede superar 20–30 segundos.

M05 — Audit log fire-and-forget sin captura de errores
Medio · Auditoría

La función audit(), duplicada en múltiples archivos de acciones, usa .then(() => {}) para ignorar silenciosamente todos los errores del audit log. Para una plataforma sujeta a auditorías gubernamentales, la integridad del log de auditoría es crítica. Si el insert al log falla, ningún sistema de alerta lo detecta.

Solución: Centralizar la función audit() en un servicio compartido, registrar errores del audit log en un sistema de monitoreo separado (Sentry, Loki, etc.) y considerar una cola de reintentos para logs fallidos.
M06 — Campo deprecated rendimientosDevueltos en interfaz activa
Medio · Calidad

La interfaz FinancialReturnsKPIs contiene el campo rendimientosDevueltos marcado con @deprecated usar valorTotalDevuelto. Mantener campos deprecated en interfaces activas obliga a los consumidores a elegir entre dos fuentes de datos y aumenta la probabilidad de usar el incorrecto en nuevas funcionalidades.

🟢 Hallazgos Bajos

Mejoras recomendadas sin urgencia operativa.

B01 — Función audit() duplicada en múltiples archivos de acciones
Bajo · Calidad

La función helper audit(supabase, payload) está copiada manualmente en modificaciones.actions.ts, financial-returns.actions.ts, update-interadmin.actions.ts y otros. Cualquier cambio en la lógica de auditoría (agregar un campo, cambiar el nombre de la tabla) debe replicarse en cada copia.

B02 — Dependencia xlsx@0.18.5 con vulnerabilidades conocidas
Bajo · Seguridad

La librería xlsx versión 0.18.5 tiene vulnerabilidades de prototipo contaminado (prototype pollution) conocidas. Aunque el riesgo es bajo dado que solo se usa en generación server-side de reportes (no en parsing de input de usuarios), debe actualizarse. Considerar migrar a exceljs como alternativa más activamente mantenida.

B03 — Archivos .gitkeep y cliente Supabase legacy no utilizados
Bajo · Limpieza

Múltiples carpetas contienen archivos .gitkeep de la estructura de scaffolding inicial (src/components/shared/, src/hooks/, src/modules/users/, etc.) que no se utilizan. El archivo src/lib/supabase.ts (cliente legacy sin sesión) parece no tener consumidores activos y puede eliminarse tras verificación.

B04 — Sin archivo .env.example documentando variables requeridas
Bajo · Operaciones

El proyecto requiere al menos 4 variables de entorno (NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, OPENAI_API_KEY) y opcionalmente OPENAI_ANALYSIS_MODEL. No existe un .env.example. El onboarding de nuevos desarrolladores o el despliegue en nuevas instancias depende de documentación verbal, lo que es un riesgo operativo.

Análisis: Arquitectura

La organización de carpetas sigue un patrón por dominio (modules/) bien aplicado. Cada módulo tiene su capa de componentes, librería de lógica y tipos. Los Server Actions (*.actions.ts) están correctamente separados de los servicios de lectura (*.service.ts).

Puntos fuertes: La separación entre Server Components y Client Components es consistente. El uso de "use server" y "use client" está bien aplicado. Los componentes de página son Server Components que pasan datos a Client Components.

Oportunidad de mejora: Algunos componentes son excesivamente grandes (interadministrativo-detail.tsx gestiona estado global del expediente). Considerar un Context Provider o Zustand store para el estado del expediente, reduciendo la propagación de props a través de múltiples niveles.

Código muerto identificado: src/modules/dashboard/.gitkeep, src/modules/financial/.gitkeep, src/modules/contracts/.gitkeep (la lógica de contratos derivados está en modules/contracts/ pero parecen ser carpetas de scaffolding).

Análisis: Base de Datos

Modelo: La DB tiene un diseño razonablemente bien normalizado para las entidades core (interadmin_adiciones, interadmin_prorrogas, etc. como tablas separadas). La excepción es la tabla interadministrativos que conserva campos calculados legacy (adicion, total_cuota_admin, etc.) — ver hallazgo M01.

Integridad referencial: No verificable desde el código, pero el uso de interadministrativo_id como FK en todas las tablas de detalle sugiere que las FK están configuradas. A verificar en el schema de Supabase.

Índices: No hay gestión de índices en el código (correctamente, eso es responsabilidad del schema de DB). A verificar: return_year y return_month en interadmin_financial_returns deben tener índice compuesto, especialmente dado que el módulo filtra por año/mes frecuentemente.

Tabla sin usar: interadmin_financial_return_repayments existe en la DB pero no tiene uso en el código. Puede eliminarse o documentarse como reservada para una fase futura de multi-pagos de devolución.

Enums: EstadoInteradministrativo y RepaymentStatus están definidos como tipos TypeScript. Si también están como enums en PostgreSQL, cualquier nuevo valor debe migrarse en ambos lados. La nota en database.ts sobre ejecutar MIGRATION_INTERADMIN_FORM.sql sugiere que esto ha ocurrido antes.

Análisis: Seguridad

Modelo de roles: Bien definido y centralizado en src/modules/projects/lib/access.ts. Las 8 funciones de acceso (canEdit, canCreate, canDelete, canEditFinancialTabs, etc.) son puras y testeables.

Validaciones backend: Todas las Server Actions validan permisos antes de operar. Las validaciones de negocio (ej. mes válido, valor > 0) están presentes en las acciones. Las URL-fields tienen validación de formato (validateUrl()).

Variables de entorno: SUPABASE_SERVICE_ROLE_KEY solo se usa en el servidor (admin.ts). OPENAI_API_KEY solo en Server Actions y API Routes. No hay exposición de claves al cliente.

Sesiones: El manejo de cookies de sesión usa @supabase/ssr correctamente. El refresh de tokens está en el middleware (cuando funcione — ver C01).

Pendiente de verificar: Las RLS Policies en Supabase. El código confía en que RLS está activo para todas las tablas propias. Si una tabla no tiene RLS activa, cualquier query con la anon key tiene acceso completo.

Inyección SQL: No hay construcción manual de SQL en el código TypeScript. Todas las queries usan el cliente tipado de Supabase. Sin riesgo de SQLi.

Análisis: Rendimiento

Problema de carga inicial: La página /proyectos/[id] realiza 12+ queries en paralelo al cargar. Aunque son paralelas (Promise.all), la respuesta de la página espera que todas terminen, incluyendo queries secundarias (tareas, avances) que podrían cargarse de forma diferida.

Re-renderizados: Los componentes grandes como rendimientos-financieros-tab.tsx calculan KPIs con useMemo (correcto). Sin embargo, algunos componentes de lista renderan filas con funciones anónimas en el render (onClick={() => ...}), lo que puede generar re-renders innecesarios en listas largas.

Server Components: El uso de Server Components está bien aplicado para la carga inicial de datos. La separación de "use client" solo donde hay interactividad es correcta.

Caché: Se usa revalidatePath después de cada mutación (correcto). No hay evidencia de caché adicional (ISR, Redis) para datos que cambian poco (listas de secretarías, categorías).

Análisis: Modelo Financiero

El motor financiero central (calcInteradminFinancials) es puro, determinista y bien documentado. Opera sobre las adiciones de la tabla normalizada, no sobre los campos legacy. Este es el enfoque correcto.

Cadena de cálculo: Valor Original → Adiciones (normalizadas) → Valor Total Actual → Distribución por fuente → Rendimientos → KPIs. Cada paso está en funciones puras y reutilizables.

Pendiente de devolución: pendientePorDevolver se calcula como la suma de gross_return_value de registros no DEVUELTO. Si un rendimiento está en estado PARCIAL (devolución en proceso), el valor total bruto se cuenta como pendiente, sin descontar lo ya devuelto. Esto sobreestima la deuda.

Valor devuelto: El patrón repayment_value ?? gross_return_value para valorTotalDevuelto es inteligente como migración, pero crea una inconsistencia: registros marcados como DEVUELTO antes de capturar repayment_value pueden mostrar un valor incorrecto si el monto real devuelto fue diferente al bruto. Recomendable agregar una bandera de migración o una nota en el registro.

Redondeo: computeDistributionRows usa Math.round(...* 100) / 100, lo que puede generar diferencias de centavos por errores de punto flotante en distribuciones de múltiples fuentes. Para contabilidad pública, se recomienda aritmética de precisión exacta (uso de enteros en centavos o librería decimal.js).

Análisis: Asistente IA

La arquitectura del módulo de IA es modular y bien diseñada: document-reader → content-cleaner → openai-analyzer → result-normalizer → result-validator. Cada paso es independiente y testeable.

Modelo usado: gpt-4o-mini (configurable vía OPENAI_ANALYSIS_MODEL). Buena elección: costo-efectivo para extracción estructurada.

Schemas: Los prompts de sistema en /schemas/ están bien estructurados con instrucciones claras. El sistema de confianza (ConfidenceBadge, result-validator) es una buena práctica para manejar extracción imprecisa.

Hub de IA: La arquitectura del IaHubModal con registro de capacidades (CAPABILITIES[]) es extensible. Agregar una nueva capacidad solo requiere añadir una entrada al array y su handler correspondiente.

Limitaciones actuales sin resolver: (1) No soporta DOCX ni imágenes escaneadas (mensajes claros al usuario, pero es una limitación real para documentos públicos). (2) No hay reintentos automáticos en fallo de OpenAI. (3) No hay caché de análisis previos del mismo documento.

Roadmap recomendado para IA: Implementar soporte DOCX (librería mammoth), OCR para imágenes escaneadas (tesseract.js o servicio externo), y un sistema de caché basado en hash del documento.

Análisis: Exportaciones

Las exportaciones Excel, Word y PowerPoint utilizan los mismos datos que el sistema de visualización. El Excel Maestro de interadministrativo usa calcInteradminFinancials y calcFacturacionKPIs — las mismas funciones que la UI. Hay consistencia.

Control de acceso: Las rutas de reporte verifican rol (REPORT_ROLES = ["ADMIN", "GERENTE", "DIRECTIVO", "GERENTE_PROYECTO"]). Sin embargo, no verifican si el usuario tiene acceso al interadminId específico, solo el rol. Un GERENTE_PROYECTO podría generar el reporte de un contrato que no le está asignado.

CORS: Las rutas API de reportes no tienen headers CORS. Si en el futuro hay integraciones desde otras aplicaciones, esto será un bloqueo.

Análisis: Logging y Observabilidad

El logging es coherente: se usa console.warn para errores recuperables (query fallida, asignación no encontrada) y console.error para errores críticos (proxy sin configuración, error de autenticación).

Todos los console.* incluyen prefijos entre corchetes ([proxy], [interadmin-access], [document-reader]) lo que facilita la búsqueda en logs de producción. Esta es una buena práctica.

Observabilidad faltante: No hay integración con un sistema de monitoreo de errores (Sentry, Datadog, etc.). En producción, los errores solo aparecen en los logs del servidor. No hay alertas automáticas cuando un Server Action falla repetidamente.

El audit log a la tabla interadmin_audit_log es bueno pero fire-and-forget — ver hallazgo M05.

Arquitectura Futura

Para soportar múltiples entidades públicas y crecer a la escala de miles de contratos, la arquitectura debe evolucionar en estas tres direcciones.

1 — Multi-tenancy por entidad

Actualmente el sistema asume una sola organización. Para múltiples entidades, agregar una dimensión entity_id (o org_id) a todas las tablas, con RLS Policies que filtren por entidad. El middleware de autenticación debe resolver entity_id desde el perfil del usuario y propagarlo al contexto Supabase.
